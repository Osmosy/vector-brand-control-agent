# Браузерный замер GEO: рецепт рабочего цикла

Когда MCP и API недоступны, а волну надо снять с живых веб-интерфейсов. Всё ниже — из рабочего
прогона: снято и проверено на живом движке, на провалах — правила, а не хроника.

## 0. Что нужно до старта

- Живые сессии в движках в браузере пользователя. Логин, 2FA и капчу проходит **он**; агент
  копирует профиль и работает под его аккаунтом, паролей не вводит.
- `agent-browser` (см. навык `agent-browser-cli`: цикл, сессии, подключение к живому Chrome).
- Каталог проекта: `<brand>/brand.json`, `<brand>/prompts.csv`, `<brand>/measurements/raw/`.

## 1. Префлайт: один запрос на движок

На каждый движок — минимальный запрос из набора и проверка трёх вещей: есть текст ответа,
есть ссылки-источники, состояние аккаунта. Различать четыре состояния, у каждого свой вывод:

| Что видно | Что это значит | Действие |
|---|---|---|
| ответ с источниками | движок годен | в волну |
| форма входа / кнопка «Войти» | профиль не авторизован | просит пользователя войти |
| «complete security verification», капча | нужна ручная проверка | открыть видимое окно, ждать пользователя |
| пустой ответ на втором-третьем запросе | гостевой лимит | не гнать волну, нужен логин |
| `no_ai_overview` (MCP AI Mode) | AI-ответа по этому запросу нет | записать как «движок не дал ответа» |

Правило: недоступный движок **не заменять молча** — сообщить, предложить замену, обновить
`measurement.engines` в брифе.

## 2. Изоляция сессий

Один браузер на движок, каждый — своя копия профиля и свой порт CDP:

```bash
rsync -a --exclude 'Cache*' --exclude 'Code Cache' --exclude 'GPUCache' \
      --exclude 'Service Worker' ~/.config/google-chrome/ /tmp/chrome-cdp2/
rm -f /tmp/chrome-cdp2/Singleton*
google-chrome --headless=new --user-data-dir=/tmp/chrome-cdp2 \
  --remote-debugging-port=9223 --no-first-run --no-default-browser-check about:blank &
agent-browser --session zai connect 9223
```

Дефолтная сессия одна на всё: фоновая волна и ручная проверка в ней перетягивают страницу
друг у друга, и в сырьё попадает чужой DOM. Параллельные движки = разные `--session`.

`--session <имя>` без `connect` поднимает **свой чистый профиль**: куки пользователя там не
живут, движок покажет форму входа на авторизованном аккаунте. Поэтому порядок обратный —
сначала Chrome на копии профиля и порт, потом `connect` этой сессией. Для третьего
параллельного движка — третья копия (`/tmp/chrome-cdp3`, порт 9224), а не второй `open` в уже
занятой сессии.

## 3. Цикл на один ответ

1. Открыть **базовый URL** движка — это и есть новый чат без истории.
2. `snapshot -i`, найти `textbox` по подсказке поля ввода; если не нашёлся — закрыть онбординг
   (`button "Close|Закрыть|Понятно|Skip"`) и повторить снимок, до 3–4 попыток.
3. `fill @ref -- "<промпт>"`, затем `press Enter`.
4. Ждать готовности: **длина текста стабильна 3 опроса подряд И нет busy-маркера**
   (`Думаю`, `Ищу `, `Отвечаю в режиме`, `Ответь быстрее`, `Thinking`, `Searching`, `Generating`).
5. Снять **контейнер ленты чата** (§3a), а не `main.innerText`: в боковой панели лежат названия
   прошлых промптов, и имя бренда из них попадает в разметку. Ссылки собирать внутри того же
   контейнера; движок без анкоров (DeepSeek) отдаёт источники только текстом — тогда домены
   вытаскивать регуляркой из ответа и честно ставить `web_search=false`, если их нет.

### 3a. Извлечение текста ответа

`main.innerText` берёт всю страницу, включая историю чатов. Контейнер ответа ищется так:
перебрать `div/main/section`, оставить элементы, чей `innerText` содержит текст промпта и
длиннее ~600 знаков, отбросить те, где встречаются маркеры сайдбара («Новый чат», «Нет истории
чатов»), и взять самый короткий из оставшихся. Дальше закрепить найденный класс как селектор
движка.

Проверенные селекторы (классы хешированные, живут до редизайна — при пустом результате
повторять поиск по правилу выше, а не править вслепую):

| Движок | Селектор ленты | busy-маркеры |
|---|---|---|
| Алиса | `[class*="AliceChat-Column"]` | `Думаю`, `Ищу `, `Отвечаю в режиме`, `Ответь быстрее` |
| DeepSeek | `.ds-virtual-list-items` | нет (генерация короткая) |
| Z.ai | — (лента в общем контейнере) | `Thought Process`, `Searches` |

Z.ai и DeepSeek-подобные движки без анкоров источников не дают: `brand_cited` для них считается
только по домену в тексте ответа, иначе метрика молча обнуляется и вина списывается на бренд.

Без busy-маркера первый же прогон снял 1 051 знак рассуждений вместо 4 623 знаков ответа:
на фазе поиска текст тоже стоит, стабилизация длины сама по себе не означает «ответ готов».

## 4. Очистка и хранение

Снятая страница содержит обвязку: сайдбар, «Новый чат», «Поделиться», рекламные блоки,
счётчики. В файле держать две секции: `## Answer (cleaned)` — по ней идёт разметка,
`## Page text (raw)` — по ней сверяются цитаты в отчёте.

В `## Answer (cleaned)` дополнительно вырезать **эхо промпта**: снятый текст начинается с
повторённого вопроса, а в промптах классов `brand` и `compare` стоит имя бренда — без вырезания
любой такой ответ автоматически получает «бренд упомянут».

### 4a. Переизвлечение уже снятого сырья

Если тексты сняты не тем контейнером, волну **не переснимать**: в шапке каждого файла лежит
`url:` чата. Скрипт переизвлечения открывает этот URL, ждёт загрузки и перезаписывает только
секции ответа и источников, оставляя шапку и имя файла. На 179 файлах это ~10 минут против
часов повторной волны; после него обязателен повторный прогон разметки и скоринга.

Формат файла `measurements/raw/<дата>-<engine>-<prompt_id>-<repeat>.md`: YAML-шапка (engine,
prompt_id, scenario_class, weight, repeat, date, url, captured, stable) + промпт + ответ +
список источников. `stable: false` — сигнал перепроверить ответ, а не молча размечать.

## 5. Пропускная способность

30–45 с на ответ на живом движке → 30 промптов × 3 повтора ≈ 45–90 мин на движок на бренд.
Запускать фоном с записью по файлу на ответ и добирать пропуски повторным прогоном: скрипт
пропускает уже снятые файлы, `--force` — только для сбойных.

## 6. Что скрипт должен уметь

- `--brand`, `--engine`, `--session`, `--prompts id1,id2`, `--limit`, `--repeats`, `--force`.
- Пропускать существующие файлы (добор после обрыва без пересъёмки).
- Писать сбой в stderr и продолжать, а не падать на первом `не нашёл поле ввода`.
- Распознавать конец сессии (страница входа, `security verification`) и **прерывать** волну с
  отдельным кодом возврата: сохранённая страница входа проходит все проверки покрытия как
  нормальный ответ, и недобор обнаруживается только на разметке.
- Не размечать: разметка — отдельный шаг, иначе автоматическая интерпретация подменит суждение.

## 7. Когда браузерная сессия не живёт: API-харнесс

Разлогин, капча и блокировка по IP у DeepSeek снимаются прямым API — один и тот же класс
измерения без браузера:

```bash
# ключ лежит в ~/.hermes/.env как DEEPSEEK_API_KEY
curl -s https://api.deepseek.com/models -H "Authorization: Bearer $DEEPSEEK_API_KEY"   # модели
curl -s https://api.deepseek.com/user/balance -H "Authorization: Bearer $DEEPSEEK_API_KEY"  # баланс в CNY
curl -s https://api.deepseek.com/chat/completions -H "Authorization: Bearer $DEEPSEEK_API_KEY" \
  -H 'Content-Type: application/json' \
  -d '{"model":"deepseek-flash","messages":[{"role":"user","content":"<промпт>"}]}'
```

- Модели: `deepseek-flash` (DeepSeek-V4.1-Flash, 1M контекста) и `deepseek-v4-pro`; ключ 35 знаков,
  баланс возвращается в USD и CNY — считать в юанях. Один ответ ≈ 6 тыс. токенов вместе с
  генерацией, то есть волна на два бренда — единицы юаней.
- Ответы API — **канал памяти**: веб-поиска нет, ссылок нет, `web_search=false` и
  `citation_share=0` по определению. Писать это в отчёт, а не выдавать за поисковый канал.
- Сырьё — тот же формат `measurements/raw/<дата>-<engine>-<prompt_id>-<repeat>.md`, но `engine`
  другой (`deepseek-api`), иначе API-строка сливается с веб-строкой того же движка.
- При 429/5xx — повтор с нарастающей паузой; при 401/402 — остановить волну: это ключ или баланс,
  а не сеть.

Если один бренд снят по API, а другой по веб-интерфейсу — в сводке считать сопоставимый срез
(«Алиса + DeepSeek API» по обоим), иначе сравнение брендов идёт по разным каналам. Веб-линия и
API-линия одного DeepSeek — одна модель в двух обвязках, а не два независимых движка.
